# PRD：双人旅行 Agent 决策层

## 0. 文档目的

本 PRD 定义“旅游计划”从共享行程板升级为双人旅行决策工具的第一阶段。它供产品、UX、架构和开发工作流共同使用：正文只定义用户价值、行为和可验收要求；数据源、浏览器复核、安全边界与已验证结论见同目录 [addendum.md](addendum.md)。它建立在既有共享行程和已确认的旅行通行证视觉设计之上；通行证首页重构本身仍是待实现工作。

## 1. 愿景

两个人计划旅行时，真正困难的不是新建某一天，而是把“我想舒服一点”“你不想太赶”“价格要真实”“到底哪家能订”变成共同能接受的方案。本产品让两位旅行者公开表达偏好，由 Agent 提出少量可解释、可追溯的候选，并把共同决定沉淀为手机端可用的行程。

这不是替用户下单的旅行社，也不是用看似精确的幻觉填满路线。它在规划期利用本地 Desktop Agent 连接真实数据和已登录网页，在旅行期让手机端稳定读取最后已核验的结果。每一个推荐都回答三个问题：为什么适合你们、数据来自哪里、最后何时核验。

## 2. 目标用户

### 2.1 Jobs To Be Done

- 当两位伴侣对住宿、餐厅、景点和节奏有不同偏好时，快速看见共同点与分歧，而不是靠聊天记录反复回忆。
- 当不知道“该做什么”时，以简单问卷启动规划，并得到 2–4 个有理由的候选，而不是面对无限搜索结果。
- 当需要花钱或锁定重要安排时，确认候选确实适用于出行日期、人数、房型/票种和关键条款。
- 当出发后 Desktop Agent 不在线时，仍能在手机上查看保存的路线、地点、最后核验时间和共同决定。

### 2.2 非用户（v1）

- 需要平台代订、支付、改签、抢票或餐厅订位的用户。
- 面向公众的大规模多人拼团、旅行社运营或商业化分销场景。
- 将高铁实时余票作为关键依赖的行程。

### 2.3 关键用户旅程

- **UJ-1：Yiming 与伴侣建立共同偏好。** 两人已登录同一共享旅行，各自填写约五分钟的偏好问卷。每份回答即时对对方公开；当两人完成或主动跳过时，系统生成共同偏好、待讨论分歧和下一步建议。若任一人修改答案，摘要重新生成，但既有行程不被覆盖。
- **UJ-2：Yiming 让 Agent 找到可信的住宿。** 他输入香港的日期和人数。Agent 使用快速数据源召回候选，再在已登录网页核验重要候选。提案卡只给 2–4 个选项，并显示适用日期、房型/条件、价格快照、位置、来源和核验时间；无法复核的项明确标为待接管。
- **UJ-3：两人逐步形成每日安排。** 任一人把酒店、餐厅或景点加入暂定行程，另一人可点赞、反对或解释原因。Agent 依据这些反馈提出替代项；出发前两人共同将暂定项设为最终确认，且之后仍可回退。
- **UJ-4：伴侣在旅行中查看行程。** Desktop Agent 已关闭，她在手机 PWA 打开旅行通行证和每日计划，读取已保存地点、路线与最后核验时间。她理解价格或库存可能已变化，不会把快照误认为持续有效的承诺。

## 3. 术语

- **偏好问卷**：两位旅行者分别完成、对彼此公开的快速点选与可选补充输入。
- **共同偏好摘要**：在两人完成偏好问卷后，Agent 对共同点、分歧和取舍的可解释汇总。
- **候选**：尚未满足网页复核条件的酒店、餐厅或景点。
- **网页核验**：在来源网页中确认旅行适用日期、人数、关键条件和事实字段的过程。
- **已网页核验候选**：拥有完整关键证据的候选；不是价格永久有效的保证。
- **暂定行程**：任一旅行者加入、仍可调整的旅行安排。
- **最终确认**：两位旅行者出发前显式确认的安排；可回退为暂定行程。
- **需要接管**：网页遇到登录、验证码、风险控制、加载失败或字段缺失，等待用户在 Chrome 中继续处理的状态。
- **证据快照**：候选的来源 URL、查询时间、适用日期、关键字段和来源系统记录。

## 4. 功能需求

### 4.1 公开偏好问卷

**说明：** 偏好问卷为不知道如何开始规划的两位旅行者提供低门槛入口，实现 UJ-1。

#### FR-1：快速点选与补充输入

每位旅行者可以完成包含住宿标准、预算范围、旅行节奏、步行/排队容忍度、餐饮偏好、景点类型与避开项的偏好问卷；每题可选填原因，“一定要有”“坚决不要”和其他补充允许自由输入。实现 UJ-1。

**验收：**
- 问卷以选项、范围或多选标签为主，不要求用户预先知道如何描述旅行需求。
- 已保存答案可编辑；编辑记录作者和时间。

#### FR-2：双方公开与共同偏好摘要

系统应即时向两位旅行者展示彼此的问卷回答；仅在两人完成或主动跳过后生成共同偏好摘要。实现 UJ-1。

**验收：**
- 摘要明确分为共同偏好、待讨论分歧与建议取舍。
- 摘要不隐藏权重，不自动替任何一方作决定。
- 问卷修改触发重新汇总，且不覆盖暂定行程或最终确认。

### 4.2 有证据的 Agent 提案

**说明：** Agent 以少量候选帮助两人做决定，而不是替代选择。实现 UJ-2、UJ-3。

#### FR-3：每轮候选的数量与理由

Agent 每轮必须给出 2–4 个候选，并针对共同偏好和已知分歧说明推荐理由。实现 UJ-2。

**验收：**
- 候选可属于酒店、餐厅或景点。
- 推荐理由引用偏好问卷、行程上下文或双方已写下的反馈。
- Agent 不可自动把候选写为最终确认。

#### FR-4：候选卡与证据快照

每个候选卡应展示类别、名称、位置、旅行适用日期、关键条件、来源、查询时间和当前状态；价格、营业信息或库存等动态数据应明确为证据快照。实现 UJ-2。

**验收：**
- 酒店的重要条件至少包括人数、房型或床型、价格展示方式及取消条件（如来源可提供）。
- 餐厅和景点的重要条件至少包括位置、营业/开放信息（如来源可提供）与适用的票种或人均价快照。
- 缺少关键字段的候选不能标记为已网页核验候选。

#### FR-5：两人反馈与迭代

两位旅行者可以对候选点赞、反对或写下理由；Agent 应在下一轮提案中保留和解释这些反馈。实现 UJ-3。

**验收：**
- 两人的反馈实时同步且带作者与时间。
- 反对或分歧不会删除对方历史反馈。
- Agent 可提出替代项，但不覆盖用户已有的暂定行程。

### 4.3 网页核验与可信度状态

**说明：** 产品明确区分候选、网页核验和最终确认，防止将聚合价格或模型推断误称为真实结果。实现 UJ-2、UJ-4。

#### FR-6：网页核验状态

系统应管理候选的 `candidate`、`web_verified`、`tentative`、`confirmed`、`needs_takeover` 与 `stale` 状态。实现 UJ-2、UJ-3。

**验收：**
- 只有适用日期、人数和关键条件均已核对的候选才可进入 `web_verified`。
- 网页被登录、验证码、风险控制、加载失败或字段缺失阻断时，候选进入 `needs_takeover`，不得伪造核验成功。
- 证据过期、价格变化、库存/房型消失时，候选降级为 `stale` 或 `candidate`，保留历史证据快照与变化原因。

#### FR-7：来源差异呈现

当快速数据源与网页结果在价格或关键条件上不一致时，系统应呈现差异，并以当前网页详情页作为最终复核来源。实现 UJ-2。

**验收：**
- 系统不得对冲突价格取平均值。
- 用户可打开来源链接并看到最后核验时间。

### 4.4 共享行程与旅行期可用性

**说明：** 暂定与最终确认既支持共同规划，也支持 Agent 离线后的旅行期使用。实现 UJ-3、UJ-4。

#### FR-8：暂定、最终确认与回退

任一旅行者可以把候选放入暂定行程；两位旅行者可以显式最终确认，且最终确认可回退。实现 UJ-3。

**验收：**
- 每次状态变化实时向两位旅行者同步，并记录作者与时间。
- Agent 不可自主执行最终确认。

#### FR-9：Desktop 离线后的 PWA 阅读

Desktop Agent 不运行时，手机 PWA 应可读取已保存的暂定行程、最终确认、地点、路线和最后核验时间。实现 UJ-4。

**验收：**
- 手机端明确区分历史快照与当前实时信息。
- 不依赖 Desktop 在线才能打开已保存行程。

## 5. 体验与信息架构

- 首要表面依次为：旅行通行证首页、偏好问卷、Agent 提案、候选详情/来源证据、每日计划。
- 视觉使用既定旅行通行证体系：米白纸张、深绿主文字、橙红日期与核验章、路线叙事和票根分隔。
- 不采用通用后台卡片、SaaS 流程图或以“AI 正在工作”为中心的界面；界面应强调共同决定和来源证据。
- 桌面优先用于规划与网页核验；窄屏/PWA 优先保证通行证、每日计划和来源快照可读。

## 6. 跨功能质量要求与约束

- **真实性：** 动态价格、库存、票务、营业与路线信息均需带来源和查询时间；无法判断真实性时明确表达不确定。
- **隐私与安全：** 前端不得存放 FlyAI/高德 Web Service 密钥、Codex 凭据或浏览器 Cookie；本地 Agent 不持久化或下发浏览器登录态。
- **交易边界：** Agent 只查询与复核，不执行下单、支付、改签、抢票或订位。
- **同步与离线：** 两人决策实时同步；旅行期支持读取已保存内容，不承诺 Desktop 离线后的实时刷新。
- **并发一致性：** 两人同时修改问卷/反馈或 Agent 写回候选时，冲突必须可见且不可静默覆盖；后续架构须兼容现有整份旅行记录的乐观版本控制。
- **可追溯性：** 每项动态事实可追溯到证据快照；历史快照不可被无提示覆盖。

## 7. 非目标

- 任何形式的交易执行或自动购买。
- 高铁查询和 12306 非官方抓取。
- 把聚合搜索价格当作最终成交价格。
- 当 Desktop Agent 关闭时继续声称所有数据实时更新。
- 将产品扩展为公众旅行服务、商业分销或多人团体系统。

## 8. MVP 范围

### 8.1 范围内

- 两人公开偏好问卷、共同偏好摘要和修改追踪。
- 酒店、餐厅、景点的候选提案、双方反馈和状态流转。
- FlyAI/高德候选数据的证据快照。
- 已登录网页的人工在环复核与需要接管状态。
- 暂定/最终确认与手机端已保存行程阅读。
- 旅行通行证视觉体系下的问卷与提案界面。
- 与现有共享旅行、成员授权、CloudBase 实时同步和离线队列兼容的持久化模型。

### 8.2 MVP 范围外

- 航班/高铁的完整比价、余票或出票流程；航班已有查询能力但不是本阶段阻塞条件。
- 直接接入携程/美团等未验证的商业交易 API。
- 自动执行任何交易。
- 旅游期间后台自动刷新或要求 Desktop 常开。

## 9. 成功指标

### 主要指标

- **SM-1：共同决策完成率。** 两人完成问卷后，至少有一项候选进入暂定行程的旅行占比。验证 FR-1 至 FR-5。
- **SM-2：可核验提案率。** 重要候选中拥有来源、查询时间和关键字段的占比；目标为 100%。验证 FR-4、FR-6、FR-7。

### 次要指标

- **SM-3：确认前返工可见性。** 所有从暂定回退或更改的记录均保留原因。验证 FR-5、FR-8。
- **SM-4：旅行期可用性。** Desktop Agent 关闭后，保存行程在手机端可读取的成功率。验证 FR-9。

### 反指标

- **SM-C1：候选数量。** 不以更多候选为成功；每轮保持 2–4 个，避免搜索结果淹没决策。约束 FR-3。
- **SM-C2：自动确认数量。** 不以更少用户操作为成功；最终确认必须由用户显式完成。约束 FR-8。

## 10. 开放问题

1. 用户已登录网页在不同 OTA、验证码和风控条件下可自动复核到什么程度，需在实现前针对目标网站建立操作许可清单。
2. [ASSUMPTION] 第一阶段以现有双人成员模型为准；若未来支持更多成员，需要另行定义投票与确认规则。
3. [ASSUMPTION] 餐厅数据可先以地点/营业信息/人均价快照和外链核验为主，不承诺实时排队或订位库存。
4. [ASSUMPTION] “两位旅行者共同最终确认”使用同一现有成员验证机制，不引入额外身份系统。

## 11. 假设索引

- §10.2：MVP 保持双人成员模型。
- §10.3：餐厅不以实时排队或订位库存作为承诺。
- §10.4：现有成员验证机制足以承载共同确认。
